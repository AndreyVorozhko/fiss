## Источники, связи и история

### Как избежать противоречий

**Основной источник (источник истины)** — место, сведения из которого проект считает определяющими для конкретного знания или вида информации. Знание в FISS канонично по умолчанию: если материал не содержит `Derived from:`, он является каноническим источником содержащегося в нём знания. Каноничность не задаётся принадлежностью к каталогу или области.

Проект может определить основные внешние источники или правила приоритета для видов информации. Например:

| Вид информации | Возможный основной источник |
| --- | --- |
| Состояние задач | Трекер задач |
| Принятые архитектурные решения | Реестр ADR |
| Проектные соглашения | Соответствующие документы в `FISS/knowledge/` |
| История изменений файлов | Система контроля версий |

Это пример распределения ответственности, а не установленная FISS иерархия. Правила проекта следует размещать там, где их найдут при работе с соответствующим контекстом; общие правила можно включить в `FISS/BOOTSTRAP.md`.

В соответствии с [принципом «Сохраняйте ясность основных источников»](./intellectual-space.md#principle-canonical), одно и то же знание не должно независимо поддерживаться в нескольких местах. Если полезны копия, пересказ, карта, схема или другое представление, ровно одно представление остаётся каноническим, а все остальные явно обозначаются как производные.

Единственный маркер производности — точный английский текст `Derived from:`. Он не локализуется, а после него должны находиться Markdown-ссылки непосредственно на исходные материалы. Следует перечислять все существенные источники, необходимые для понимания происхождения и проверки представления:

```markdown
Derived from:
- [Архитектура проекта](../../knowledge/project/architecture.md)
- [Предметная область платежей](../../knowledge/subject/payment.md)
```

Это правило относится к дублированию знания, а не к совпадающим фрагментам текста или полезным различиям представлений. Краткая схема архитектуры и подробное описание могут существовать одновременно, если схема через `Derived from:` указывает описание и другие существенные источники. Производное знание не становится каноническим только вследствие существования; при изменении источников его следует пересмотреть.

При противоречии нельзя молча выбрать удобную версию. Нужно применить явно установленное правило приоритета. Если такого правила нет, выбор источника требует отдельного решения команды.

### Как связывать материалы

Связи выражаются обычными Markdown-ссылками и коротким пояснением. Отдельный язык отношений не требуется.

Например, из `FISS/state/adr/payment-decision.md`:

```markdown
Это решение закрывает [вопрос о модели оплаты](../../state/open-questions/payment-model.md).
```

Двухстрочный формат с маркером условия чтения (`Read when:`) обязателен для навигационных ссылок в индексах. В содержательных документах достаточно обычного пояснения связи.

### Когда нужна история внутри документа

История изменений не обязательна в каждом артефакте. Для файлов под контролем Git техническая история уже доступна в репозитории; проект может использовать и другую систему контроля версий.

Статус или пояснение изменения полезны, когда без них можно неправильно применить материал. Например, для решения можно указать, что оно актуально, заменено другим или отменено, и дать ссылку на новое решение. Такие обозначения и необходимость отдельной истории определяет команда.
