## Как устроена навигация

### Индекс определяет применимость контекста

`FISS/INDEX.md` — основная точка входа. Индексы отдельных областей также называются `INDEX.md` и находятся внутри соответствующих каталогов.

Главная задача индекса — отвечать на вопрос: **«когда этот материал является применимым контекстом для работы?»**, а не пытаться предсказывать конкретные низкоуровневые операции (чтение или изменение файла).

Маркер `Read when:` обозначает **условие применимости контекста** (вход в рабочий контекст). Это не просто механическая команда «открыть файл для чтения», а определение ситуационного триггера, при котором материал должен быть включён в рабочий контекст человека или ИИ-агента.

Каждый элемент навигации в индексном файле строится по строгой трёхзвенной схеме:

```text
navigation link
    ↓
reading condition marker (условие применимости: Read when:)
    ↓
non-empty condition (ситуационный триггер)
```

Стандарт закрепляет **строго двухстрочный формат** для каждой навигационной ссылки:
1. Первая строка — Markdown-ссылка на целевой документ или индекс: `- [Заголовок](цель)`
2. Вторая строка — привязанная строка с отступом в 2 пробела, содержащая явный маркер условия чтения и непустое условие: `  Read when: условие`

Маркер условия чтения всегда оформляется строго на английском языке: `Read when:`. Переводить или локализовать маркер (например, как `Читать, когда:`) не допускается. Это обеспечивает детерминированную работу автоматических линтеров (например, `fiss-lint`) и инструментов статического анализа, избавляя их от необходимости определять язык или поддерживать эвристики для произвольных вариантов перевода.

Пример корневого индекса для проекта с несколькими областями:

```markdown
# Интеллектуальное пространство проекта

- [Базовый контекст](BOOTSTRAP.md)
  Read when: начинается работа с проектом или требуется первичная ориентация.
- [Предметная область](knowledge/subject/INDEX.md)
  Read when: изменяются бизнес-правила или ведётся работа с предметными понятиями.
- [Устройство проекта](knowledge/project/architecture.md)
  Read when: требуется изменить компоненты системы или произвести настройку окружения.
- [Текущее состояние](state/INDEX.md)
  Read when: риски, открытые вопросы или временные ограничения могут повлиять на задачу.
```

### Вход в контекст и почему нет «Modify when»

Иногда возникает вопрос: если участники проекта не только читают материалы, но и изменяют их, не нужен ли отдельный маркер вроде `Modify when` («Изменять, когда»)?

В FISS намеренно **нет маркера `Modify when`**, и вводить его не следует по принципиальным причинам:

1. **`Read when` определяет вход в контекст, а не файловую операцию.** Индекс определяет, в какой ситуации материал должен стать частью рабочего контекста задачи.
2. **Изменение файла — естественное следствие работы в этом контексте.** Если агент или разработчик изменяет архитектуру проекта, он обязан обратиться к материалу, описывающему архитектуру (`Read when: требуется изменить компоненты системы...`), а завершив работу — привести его в соответствие с новой реальностью.
3. **FISS не управляет жизненным циклом файлов.** Стандарт определяет организацию и навигацию пространства, оставляя процессы и жизненные циклы на усмотрение проекта. Введение `Modify when` начало бы превращать навигационный механизм в язык управления жизненным циклом файлов и перегружать синтаксис навигации избыточными маркерами.

Модель работы с контекстом предельно чиста:

```text
INDEX
  ↓
Read when (определяет применимый контекст)
  ↓
агент или разработчик изучает материал
  ↓
работает с ним / использует контекст в задаче
  ↓
если работа изменила то, что материал описывает
  ↓
материал обновляется по результатам работы
```

Индекс отвечает на вопрос: **«когда этот материал нужен?»**, не пытаясь предсказывать, какие именно действия агент будет предпринимать после открытия документа.

### Устранение неоднозначности

Распространённый антипаттерн в произвольной документации — оформление ссылок в виде пассивных аннотаций или ссылок на каталоги:

```markdown
- [Project Knowledge](knowledge/project/) - Содержит знания проекта.
```

Такая запись нарушает стандарт сразу по нескольким причинам:
1. **Ссылка на каталог без индекса**: навигационная ссылка обязана вести на конкретный файл (`.md`) или `INDEX.md` составной области, а не на нетипизированную директорию файловой системы.
2. **Отсутствие маркера**: нет обязательного маркера условия чтения (`Read when:`).
3. **Пассивное описание вместо условия**: фраза «Содержит знания проекта» лишь сообщает, что лежит внутри, но не объясняет ситуационный триггер — в какой рабочей ситуации человеку или агенту требуется загрузить этот контекст.
4. **Однострочный формат**: условие чтения должно располагаться на отдельной строке с отступом в 2 пробела.

Подпись «Предметная область» только описывает содержание. Условие «Read when: изменяются бизнес-правила...» помогает точно решить, является ли материал применимым контекстом для текущей задачи — это реализует [принцип «Делайте применимость видимой»](./intellectual-space.md#principle-context-aware).

Наличие строгого двухстрочного формата и явного маркера делает навигацию надёжной и легко проверяемой: автоматические линтеры (например, `fiss-lint`) и навыки верификации (`fiss-validate`) могут однозначно валидировать корректность навигационной структуры без эвристических догадок.

Следуя [принципу «Отделяйте навигацию от содержания»](./intellectual-space.md#principle-context-first), индекс должен оставаться кратким: ссылки, условия применимости контекста и необходимые пояснения для навигации. Подробное содержание размещается в документах, на которые он ссылается. Это позволяет переходить от общего контекста к подробностям по мере необходимости.

### Область может быть файлом или каталогом

**Область** — тематически связанная часть интеллектуального пространства, например проектные знания или открытые вопросы.

| Форма | Когда использовать | Правило оформления |
| --- | --- | --- |
| Один файл | Тема помещается в одном документе | Имя определяется проектом |
| Каталог с `INDEX.md` — составная область | Тема разделена на несколько материалов | `INDEX.md` служит точкой входа в область |
| Каталог без `INDEX.md` — контейнер | Нужно только сгруппировать области | Ссылки на дочерние области находятся в индексе охватывающей области |

Например, `FISS/knowledge/` может быть контейнером:

```text
FISS/
├── INDEX.md
├── BOOTSTRAP.md
└── knowledge/
    ├── project/
    │   └── architecture.md
    └── subject/
        ├── INDEX.md
        ├── access.md
        └── notifications.md
```

В этом примере корневой индекс ссылается на `FISS/knowledge/project/architecture.md` и `FISS/knowledge/subject/INDEX.md`. Индекс `FISS/knowledge/subject/INDEX.md` ведёт к материалам своей области. Отдельный `FISS/knowledge/INDEX.md` не нужен.

Имена областей, представленных одним файлом, и других содержательных документов, таких как `access.md`, определяет проект. Стандарт закрепляет имена `INDEX.md` для навигационных точек и `BOOTSTRAP.md` для обязательного базового контекста.

Все используемые области должны быть доступны через навигацию от `FISS/INDEX.md`. Индекс составной области должен вести к её материалам и дочерним областям; при переходе через контейнер ссылки ведут непосредственно к вложенным областям. Для всех индексных ссылок действует строгое правило двухстрочного формата с маркером условия чтения.

### Как расширять область

Когда одному файлу становится тесно, его можно заменить каталогом с индексом:

```text
До:                         После:
FISS/state/                 FISS/state/
└── open-questions.md        └── open-questions/
                                ├── INDEX.md
                                ├── payment-model.md
                                └── access-policy.md
```

При таком переходе необходимо обновить входящие ссылки. К новому `INDEX.md` применяются те же правила навигации, что и к корневому.

### Закладывайте структуру для разделения

В областях, представленных одним файлом, рекомендуется изначально закладывать структуру, которую легко будет разделить по отдельным файлам, когда документ разрастётся. Это помогает следовать [принципу «Начинайте с малого»](./intellectual-space.md#principle-compact): начинать с простого единого файла, но заранее исключать трудности при будущем разделении.

Если материал внутри файла с самого начала организован по логически цельным разделам и подразделам, то при росте проекта каждый такой раздел становится естественным кандидатом на вынесение в отдельный файл или подкаталог без необходимости распутывать и переписывать связанный текст.

Например, начальный документ `FISS/knowledge/project/architecture.md` может содержать:

```markdown
# Frontend

## Общие правила

- В `admin` и `front` использовать TypeScript, не JavaScript.
- В TypeScript не ставить `;` в конце строк.
- Не дублировать типы между страницами.
- Для взаимодействия с backend предпочитать composable-first подход.

## Admin

- `admin` — Nuxt 4 SPA + `naive-ui`; SSR выключен.
- `admin` SPA обслуживает два host-а: admin host для `/admin` и business host для `/business`; не добавлять cross-host редиректы, раскрывающие admin host бизнес-пользователям.
- Для backend-запросов использовать `admin/app/utils/apiFetch.ts`, не прямой `fetch`.

# Cache

## Redis clients и разделение DB

- Redis разделён по ответственности:
  - DB0 / `snc_redis.token_store` / prefix `token:` — только refresh-token whitelist и auth/token storage.
  - DB1 / `snc_redis.app_cache` / prefix `cache:` — только application cache.
- Application cache не хранить в DB0.
- Auth/session/token data не хранить в DB1.
- Cache не является source of truth. Источником истины остаются PostgreSQL и доменные сервисы.

## Правила application cache

- У каждой application cache entry должен быть конечный TTL.
- Cache key должен учитывать все request parameters и context values, которые могут изменить response.
- Cache key должен быть детерминированным и стабильным для эквивалентных запросов.
- В cache key нельзя писать raw user input, токены, cookies, секреты, raw ПДн, полный URL с query string или request body.
- Если в будущем для cache key неизбежно нужен пользовательский ввод, сначала нормализовать его и предпочитать safe hash/fingerprint вместо raw value.
- При добавлении или изменении кеша в той же задаче фиксировать invalidation strategy.
- Если invalidation coarse-grained, явно фиксировать это и держать TTL консервативным.
```

Когда этот файл разрастётся, чёткая структура позволит естественным образом разделить его, например, на:

- `FISS/knowledge/project/frontend/common-rules.md`
- `FISS/knowledge/project/frontend/admin.md`
- `FISS/knowledge/project/cache.md` (или `FISS/knowledge/project/cache/INDEX.md`)
